## checkpoint.py / train.py (implemented Session 5 Half 2)

- `save_lora(model, out_dir, meta) -> Path` writes `adapter.safetensors` (only `lora_` keys) and a
  `lora_config.json` sidecar. The sidecar's target_modules / rank / alpha / dropout / adapter_dtype
  are read from the `LoRALinear` modules, not from the caller. `meta` must contain `step` and
  `config_sha256` and may not override those model-derived fields. `git_commit` gets `+dirty` if
  the worktree is dirty.
- `load_lora(model, ckpt_dir) -> model` takes an UN-injected base. It checks the sidecar's
  `base_model == model.config.name_or_path`, calls `inject_lora` from the sidecar, pre-checks
  shapes / dtypes, then asserts no unexpected keys, every saved key consumed, model `lora_` params
  == saved keys, tensors `torch.equal`, and at least one nonzero `lora_B` ("adapter is a no-op").
- `train.main(cfg, limit_examples=None, overwrite=False) -> model` steps, in order:
  1. Refuses to start if `out_dir/final/` exists (`--overwrite` removes only `final/` and `step_*/`).
  2. Writes `config.yaml` and `data_report.json` (real data drops exactly `baseball_1: 82`;
     8,577 kept).
  3. Seeded shuffle; `data_order_sha256` covers both order and token ids.
  4. Step count is FLOOR (536 steps for qv_r8).
  5. OOM preflight: forward + backward on the longest example, with no optimizer step.
  6. Token-weighted `accumulate_window`, then `log.jsonl` + `step_<n>/` + `final/`.
  7. The time-budget guard saves `final/` and logs `stopped_by_budget`.
- Testable helpers: `lr_lambda`, `warmup_steps`, `compute_total_steps`, `accumulate_window`,
  `config_sha256`.
- Smoke-test knob: `--limit-examples N` truncates after the shuffle and the length filter.

`inject_lora` is already built and its signature is fixed by `eval/runner.py` (which calls it by
keyword and assigns the result directly): `inject_lora(model, target_modules, rank, alpha, dropout)
-> model` (returns the model alone, not a tuple). It freezes the whole base model before wrapping.
Do not change this signature without updating `runner.py`.

## data.py contract (implemented Sessions 4–5 — do not change signatures without updating runner.py)

`eval/runner.py` imports `Example`, `encode_prompt`, `load_examples` from `lora_sql.data` and
destructures `.db_id` / `.question` / `.query`. As built:
- `Example` is a dataclass with `db_id`, `question`, `query`, and `schema` (the rendered DDL).
- `format_prompt(example) -> str` — receives NO tokenizer; NO ChatML at this layer. Renders schema
  (CREATE TABLE DDL: columns+types, PRIMARY KEY, FOREIGN KEY, skipping the `-1 *` wildcard) then
  the question, ending at `SQL: `. It is the user-turn *text* only, never tokenized directly —
  `encode_prompt` wraps it.
- `load_examples(path, tables_path=None) -> list[Example]` — single positional arg is what
  `runner.py` calls; `tables_path` defaults to `Path(path).parent / "tables.json"`. Schema is
  cached per-`db_id` inside each call.
- `render_schema(table_entry) -> str` — public, takes a whole `tables.json` entry; golden-string
  tested byte-for-byte against the real `perpetrator` entry. It also handles BIRD (Session 8):
  nested composite `primary_keys` are flattened into one `PRIMARY KEY (a, b)` line, and BIRD's
  type names (integer / real / date / datetime) are mapped. A BIRD golden-string test covers this.
- `load_bird_examples(path, tables_path, use_evidence=True) -> list[Example]` (Session 8) reads
  BIRD's `SQL` key. With evidence, `question = f"{q}\nHint: {evidence}"` (no hint when the
  evidence is empty). The prompt template is untouched. `runner.load_eval_examples(cfg)` picks
  between this loader and `load_examples` by `data.format`.
- `encode_prompt(tokenizer, example) -> list[int]` (Session 5) — ChatML `[system=SYSTEM_PROMPT,
  user=format_prompt(example)]` with `add_generation_prompt=True`, normalized from the v5
  `BatchEncoding` to `list[int]`. The single source of prompt ids for train AND eval;
  `runner.generate_sql` uses it (with an explicit attention mask).
- `build_train_example(tokenizer, example) -> (input_ids, n_completion)` (Session 5) —
  `encode_prompt(...) + query ids + [<|im_end|>]`, concatenated at the ID level (never a re-tokenized
  joined string); asserts `<|im_end|>` is the tokenizer's eos. The last `n_completion` ids carry loss.
  `scripts/toy_train.py` keeps its own frozen `build_example` (it produced a committed figure).

## Eval architecture (`src/lora_sql/eval/`)

The eval pipeline is generate → execute → score, split across three modules with a clean
separation of concerns — keep new eval code in the matching module rather than adding a fourth:

- `runner.py` — orchestration only, in this order:
  1. `check_held_out(cfg)`.
  2. `gold_preflight` executes every gold query BEFORE the model loads and caches the rows.
  3. `load_model_for_eval` uses `qlora.load_model` (nf4 or plain). With `--lora-checkpoint DIR` it
     calls `checkpoint.load_lora`; without one it is the plain base, with no injection.
  4. Generates greedily: `decoding_config(cfg)` -> `do_sample=False` plus an explicit
     `repetition_penalty` from `eval.repetition_penalty`; prompt ids from `encode_prompt`.
     `generate_sql(model, tokenizer, example, max_new_tokens, device, repetition_penalty)`
     returns `(sql, n_new_tokens, truncated)`.
  5. Writes a per-example `.jsonl` as it goes, then `{"summary", "meta", "results"}` to `--out`
     (or `eval.results_path`). Each `.jsonl` row has `n_new_tokens` and `truncated`. `summary`
     adds `n_pred_exec_errors` and `n_truncated`; `meta` holds the checkpoint sidecar, `decoding`
     and `eval_git_commit`. `--limit N` is for smoke tests only.
- `execute.py` — SQLite execution and comparison, no model/tokenizer code.
  - `run_query` opens the DB **read-only** (URI `mode=ro`, so writes raise and a missing file is
    never created). It enforces a wall-clock **deadline** via `set_progress_handler` (default
    30 s; sqlite's `timeout` is only a lock wait), always closes the connection, and turns any
    failure into `ExecutionError`.
  - `results_match(pred, gold, ordered)` is a NULL-safe `Counter` multiset compare with float
    rounding. It compares row order only when `order_matters(gold_sql)` (the gold has ORDER BY,
    the test-suite convention). Columns are compared positionally, with no permutation search, so
    it is slightly stricter than the official test-suite eval.
  - `execute_and_compare(db, pred_sql, gold_rows, ordered) -> (correct, exec_error)`.
  - `bird_set_match(pred, gold)` is BIRD's official rule, `set(pred) == set(gold)` (no rounding,
    duplicates and order ignored). It is for reporting only; the harness scores with
    `results_match`.
- `metrics.py` — aggregation over `EvalResult` dataclasses into a `MetricsSummary`, with an
  overall accuracy plus a breakdown by `difficulty`. It also holds the Spider difficulty code:
  - `eval_hardness(sql)` + helpers, vendored verbatim from taoyds/spider `evaluation.py` (pinned
    commit, Apache-2.0, license copy in `licenses/spider-LICENSE`). Upstream quirks are kept on
    purpose; "fixing" them breaks the official split.
  - It runs on the parsed `sql` dict that ships with each dev.json record, so `process_sql.py` is
    not vendored.
  - `eval_difficulties(path) -> list[str]` (formerly `spider_difficulties`) returns one label per
    record, in file order: the Spider tier from `sql`; otherwise the record's own `difficulty`
    (BIRD: simple / moderate / challenging); otherwise `"unknown"`.
  - Dev splits 248 / 446 / 174 / 166, and a CPU test enforces it.
  - `runner.run_eval` joins the tiers onto the examples by index and passes `difficulty=` into
    `EvalResult`.
  - Paired statistics shared by both summary scripts: `mcnemar_p` (exact two-sided), `holm`, and
    `bootstrap_ci` (95%, percentage points, over shared index resamples), and
    `cluster_bootstrap_ci(a, b, groups, n_boot, seed)` (resamples whole databases).

## Hard rules
- **Decoding parameters are always explicit.** Never rely on `model.generation_config`: Qwen ships
  `repetition_penalty: 1.1` (and `do_sample: true`), and `generate()` applies the penalty under
  `do_sample=False` too. Any new `generate()` call must pass `do_sample` and `repetition_penalty`
  itself, and any reported number must record them (`meta.decoding`).
- `data/spider_data/test.json` and `test_database/` are HELD OUT. Never read them, never
  evaluate against them, never tune on them. `database/` is the only execution target.
- Never use `base_layer.weight.shape` to get layer dimensions. Under bitsandbytes `Linear4bit`
  the weight is packed and its shape is wrong. Read `.in_features` / `.out_features`.
- transformers is pinned to 5.14.1 (v5). Use `dtype=`, never `torch_dtype=`.
  `apply_chat_template` returns a BatchEncoding: `.to(device)` + `model.generate(**inputs)`.
- Parity tests run in fp32. bf16 carries ~3 significant decimal digits and cannot reach
  atol=1e-6. Training: 4-bit base with bf16 compute, LoRA adapters fp32, no `torch.autocast`,
  explicit casts in `LoRALinear` that mirror peft's order. Never call
  `peft.prepare_model_for_kbit_training` and never upcast base params — it fp32-casts the untied
  embed + lm_head (4.36 GB).
- Prompt ids come only from `data.encode_prompt` (ChatML + `SYSTEM_PROMPT`), in both train and eval.
- Training files are only `train_spider.json` / `train_others.json`. `config.py` enforces this;
  dev is eval-only.
- LoRA checkpoints go through `checkpoint.save_lora` / `load_lora` only. Never call a bare
  `load_state_dict(strict=False)`.
- Training is micro-bs 1 with token-weighted gradient accumulation and completion-only logits
  (`logits_to_keep`).
- peft `scaling` is a dict `{"default": alpha/r}` — index `["default"]`, never assume it's a
  scalar. (Session 3.)
- Parity / weight-transplant tests must randomize peft's `lora_B` before copying, or the
  comparison is vacuous (`base == base`) and `lora_A.grad` is zero. (Session 3.) NOTE: this is a
  TEST-ONLY technique — real training (and the toy loop) must leave `lora_B` at zero-init.
- LoRA checkpoints: save only keys containing `lora_`, and after `load_state_dict(..., strict=False)`
  assert `unexpected_keys == []` and that the expected lora keys were consumed. `strict=False`
  silently loading nothing is a real failure mode here. This is the highest-value trap in the project.
- Qwen2.5 pad (`<|endoftext|>`) and eos (`<|im_end|>`) are DISTINCT token IDs — add
  `assert pad_id != eos_id` once batching (bs>1) starts in Week 2, so pad-masking never clobbers eos.
- Ablations are new files in `configs/`, never edited copies of `train.py`.
- GPU is an RTX 4060 Laptop, 8.2 GB VRAM. Assume memory is tight.
- **Parity tests must include a non-power-of-two scaling case** (e.g. r=8, alpha=12 → 1.5).
  Power-of-two scaling is exact in every float format and commutes with dtype casts, which hides
  cast-order bugs. Every training config uses alpha=2r (scaling 2.0), so training configs alone
  can never catch this. (Session 5: the pre-1a order was off by 0.32 at scaling 1.5, 0.0 at 2.0.)
- `LoRALinear` cast order mirrors peft 0.19.1 bnb `Linear4bit.forward` exactly: `x` → adapter dtype
  (fp32) BEFORE dropout; `lora_B(lora_A(dropout(x))) * scaling` in fp32; output → base output dtype,
  then add. Do not reorder; 4-bit parity is bit-identical only in this order.
- All `configs/train/*.yaml` share identical data settings (`max_seq_len` 2048, train files, seed);
  ablations differ only in `run_name`, `lora.*`, `train.out_dir`. A test enforces this.
